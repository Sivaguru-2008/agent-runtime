The silent failure mode

An agent issues a $150 Stripe refund. The next step — logging it to your database — times out. Your retry logic fires and re-runs the agent's plan. The agent calls Stripe again.

You just refunded the customer twice. LLM agents plan steps dynamically, so a naive retry re-runs the whole plan — every external call repeats. Money moves twice. State corrupts.

See a worker crash mid-refund — and recover safely

Kill the worker mid-execution. A standby hydrates from the last checkpoint, skips the already-done refund (fenced 🔒), and finishes the ledger write. Charged once.

How it works

1 · Event sourcing

Every step is an append-only event, not a mutable row that races under recovery. State is rebuilt by replaying the log.

2 · SQL-level fencing

Each side effect reserves a deterministic idempotency key in the same transaction that validates the worker's fence token. A stale worker is rejected at the database.

3 · Deterministic replay

Rewind any failed run from any point. A chain-hash divergence detector makes replays verifiable — you can prove no external call was duplicated.

One Node process + Postgres. No Redis, no Kubernetes to try it.
